### Task 2: Formatter (fmt-maven-plugin)

- **Satisfies:** DW-4. Issue task: "format locally, check in CI".
- **Files:** `pom.xml` (already edited, unstaged).
- **Test first (deliberate break):**
  1. Add a badly formatted class, e.g. `FormatProbe.java` with odd spacing, under `src/main/java`.
  2. Run `./mvnw verify`. It must FAIL at the `fmt:check` goal.
  3. Run `./mvnw fmt:format`, then `./mvnw verify`. It must pass.
  4. Delete the probe.
- **Minimal code:** find out which phase the `check` execution actually runs in (the plugin's default is unconfirmed; CLAUDE.md claims `validate`, and the `pom.xml` execution sets no phase). Check with `./mvnw help:describe -Dplugin=com.spotify.fmt:fmt-maven-plugin -Dgoal=check -Ddetail` or the build log.
  - **Done means one of two outcomes**, and CLAUDE.md must match the result:
    - Add `<phase>validate</phase>` to the execution so the format check fails fast before tests. Preferred.
    - Or accept the plugin's default phase and correct the CLAUDE.md sentence.
- **Line endings (Windows):** Git already warns that `pom.xml` will be converted to CRLF here, and it is unconfirmed whether google-java-format treats CRLF Java files as unformatted.
  - Test it: check out the files with CRLF (`core.autocrlf=true`), run `./mvnw fmt:check`, and compare with CI's LF result.
  - If CRLF fails the check, add `*.java text eol=lf` to `.gitattributes`. Do this either way if the test is inconclusive, because otherwise the hook in Task 5 can keep rewriting files.
- **Format the scaffold:** run `./mvnw fmt:format` once. The scaffold uses tabs, and google-java-format uses 2-space indentation, so the existing four test/main classes will be rewritten. Commit that reformat separately from the plugin addition to keep the diff reviewable.
- **Verify:** the break fails, the fix passes, and `fmt:check` passes on a clean checkout.
- **Commits:** `Add fmt-maven-plugin`, `Pin Java line endings to LF` (if needed), then `Format scaffold sources`

### Task 5: Pre-commit formatter hook

- **Satisfies:** the issue task "Pre-commit hook running the formatter" (supports DW-4 locally).
- **Files:**
  - Create `.githooks/pre-commit`, a POSIX sh script, stored with LF line endings. `.gitattributes` must keep it `eol=lf` so it works from Git Bash on Windows.
  - Mark it executable in git: `git update-index --chmod=+x`.
- **Behaviour:**
  1. Collect the staged `*.java` files. If there are none, exit 0.
  2. Run `./mvnw -q fmt:format`.
  3. If the formatter changed any of the staged files, do not re-stage them silently. Abort the commit and print "files were reformatted, review and `git add` them, then commit again". Re-adding would stage unstaged hunks and break `git add -p`.
  4. Exit non-zero if the formatter itself fails.
  - Because `fmt:format` rewrites the whole tree, it can also touch unstaged files. After Task 2's one-off reformat this should be a no-op. If it isn't, switch to formatting only the staged files.
- **Activation:** `git config core.hooksPath .githooks`. Git does not version this setting, so document the one-time command in CLAUDE.md. Optionally add a Maven or script step later; not in scope.
- **Test first:**
  1. Stage a badly formatted Java file.
  2. Run `git commit`. It must abort with the reformat message, and the file in the working tree is now formatted.
  3. Re-stage and commit again. It must succeed.
  4. Confirm a commit with no Java files skips the formatter.
  5. Confirm `git add -p` of one hunk leaves the other hunk unstaged after the hook runs.
- **Commit:** `Add pre-commit formatter hook`
